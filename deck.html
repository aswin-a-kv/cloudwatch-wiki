AWS Logging & Observability

Monitoring with Amazon CloudWatch

Start with the fundamentals — metrics, logs, alarms, dashboards, and traces — then move on to what matters beyond the basics.

Observability: the three pillars

You can't walk over to a cloud server and look inside. So the system gives off signals, and you read them from the outside. Almost every tool, CloudWatch included, is built on three kinds.

  • Metrics — numbers over time ("CPU at 80%"). Cheap, great for graphs and alerts. Tell you that something is wrong.
  • Logs — text records of individual events ("payment declined for order 8842"). Carry the detail. Tell you what happened.
  • Traces — one request's journey across services ("3s checkout, 2.8s in the DB"). Tell you where it happened.
Kitchen analogy

Metrics are the gauges, logs are the order tickets on the rail, traces are following one order from grill to table. The whole point of CloudWatch: all three in one place.

Why CloudWatch, and a map of the console

AWS's native monitoring service. Its edge: almost every other AWS service already pushes metrics and logs into it automatically — you wire nothing up. X-Ray (tracing) and Application Signals (APM) now live in the same console too.

  • Logs, Metrics, Alarms — the three you'll use 90% of the time.
  • X-Ray traces, Dashboards, Application Signals — tracing, custom graphs, automatic APM.
  • Insights family, RUM & Synthetics, Network monitoring — curated deep-dives and user-side views, reached for a specific need.
Everything is per RegionApp in Mumbai, console on N. Virginia = an empty screen. Always check the Region selector top-right first.

Metrics: numbers measured over time

Strip the jargon and a metric is a list of (time, number) pairs. 10:00 → 45, 10:01 → 52. CloudWatch stores them and draws the line.

  • Namespace = the folder (AWS/EC2, AWS/Lambda, or your own). Dimensions = labels that pin it to one thing (InstanceId=i-0abc).
  • Three sources — AWS services publish automatically, the CloudWatch agent reports host-level (memory, disk), your code emits custom metrics via PutMetricData.
  • Statistic matters — same data, pick Average / Sum / Maximum / p99. For latency, p90/p99 tells a truer story than average.
The one-liner

AWS/EC2 → CPUUtilization → InstanceId=i-0abc is one unique line on a graph. Namespace is the cabinet, metric name the folder, dimensions the label.

Logs: three nested boxes

A log is a line of text written when something happens. CloudWatch Logs collects, keeps, and searches them. The console is organized exactly this way:

  • Log event — one line. A timestamp plus a message.
  • Log stream — events from one source (one container, one Lambda env). One worker's notebook.
  • Log group — all streams for one app (/aws/lambda/checkout). You set retention and permissions here, and search all streams at once.
How logs get in

Native AWS integration (VPC Flow Logs, API Gateway), Lambda automatically (anything you print), the CloudWatch agent tailing files on EC2/ECS/EKS, or your code via PutLogEvents.

Logs: retention, cost, and classes

The mistake that costs real money: by default, logs are kept forever, and CloudWatch charges for storage.

  • Retention — set per log group, 1 day to 10 years or never expire. Set 30–90 days on every group. The #1 cost tip.
  • Log classes — Standard (full features, actively queried) vs Infrequent Access (cheaper, "must keep, rarely read" / compliance).
  • Encryption — log groups can be KMS-encrypted for security-conscious workloads.
Worked example

A group you never read but must keep 7 years for compliance? Set a 7-year retention and switch it to Infrequent Access.

Making logs useful: query, tail, filter

The value isn't storing millions of lines — it's getting answers out fast.

  • Logs Insights — a query tool that reads as a pipeline: pick fields, filter, aggregate, sort. Recent consoles add a natural-language query generator.
  • Live Tail — new events stream to your screen the instant they're written, like tail -f in the browser. Metered — stop when done.
  • Metric filters — watch a log group for a pattern (e.g. ERROR) and bump a metric each match. Log text becomes a number you can alarm on. Not retroactive — set up early.
fields @timestamp, @message
| filter @message like /ERROR/
| sort @timestamp desc
| limit 20

Alarms: monitoring becomes alerting

A graph nobody watches at 2am is useless. An alarm watches a metric for you and acts when it crosses a line.

  • The pieces — a metric (with statistic + period), a threshold and comparison, and evaluation periods ("3 of 3 five-minute periods above 80%") to avoid paging on a blip.
  • Three states — OK, ALARM, and INSUFFICIENT_DATA (not broken — CloudWatch just can't see enough data; a stopped or brand-new resource sits here).
What firing does — the action

Notify a human via an SNS topic (email, SMS, Slack, PagerDuty), trigger EC2 Auto Scaling to fix it, or route through EventBridge to a Lambda for custom logic.

Dashboards: the picture on one screen

A custom page where you pin the graphs and numbers that matter, so you glance at one screen instead of hunting menus.

  • Widgets — a line graph, a single big number, a gauge, an alarm-status panel, a Logs Insights result, or a text note.
  • One-click add — any Metrics graph or Logs Insights result drops onto a dashboard; no starting from scratch.
  • Cross-service, cross-Region, cross-account, shareable — one page can show the whole stack, even to people without an AWS login.
The real skill

Not building a dashboard — choosing the few graphs that tell you the system is healthy, instead of forty widgets nobody reads.

Tracing with X-Ray: following one request

The metric says "slow." The logs are scattered across ten services. Which one is the culprit? That's what tracing solves — it follows one request through every hop and times each.

  • Segment = one service's work on a request. Subsegment = a slice inside it ("200ms was the DynamoDB call"). Trace = all segments for the same request, stitched together.
  • Trace ID travels with the request like a relay baton — every service writes its segments under the same ID. Sampling records a representative subset, not every request.
  • Instrumentation needed — Lambda/API Gateway active tracing (a checkbox), the X-Ray SDK, or increasingly ADOT (OpenTelemetry).
Reading it

The service map turns a sick node red; the segments timeline is a waterfall where the widest bar is your bottleneck.

Application Signals & the rest of the toolkit

Everything so far is building blocks. Application Signals is the newer APM layer that does the golden-signal monitoring for you — volume, latency, errors, availability per service, an auto-discovered service map, and SLOs.

SLOs

A promise as a number ("checkout under 300ms, 99.9% of the time"), with error-budget tracking. The console can now recommend targets.

Curated deep-dives

Container / Lambda / Database Insights for a specific workload; RUM and Synthetics for the user-side view.

Mental model

X-Ray and raw metrics are the engine; Application Signals is the dashboard on top that already knows what "healthy" looks like.

What matters beyond the basics

Logs, custom metrics, smarter alarms, X-Ray search, observability quick wins, and where Synthetics/RUM fit.

Logs, beyond filter & export

  • A query can be a graph — stats … by bin(5m) + display, not just a filtered list.
  • Log anomaly detection — zero-config, per log group, trains on two weeks of history and flags new or abnormal patterns.
  • Three paths to CloudWatch — native push, the CloudWatch agent, or EMF (a log line parsed into a metric).
fields @timestamp, latency, path
| stats pct(latency, 95) as p95 by path
| sort p95 desc
| limit 20

Log group protections: deletion, masking, visibility

Deletion protection

One flag, off by default. Once on, any delete attempt is blocked until it's explicitly turned off again — no more "someone fat-fingered a delete."

Data Protection: Audit + Deidentify

Audit finds matches and can route findings to a destination. Deidentify is the part that actually masks the value on display, with asterisks — applied going forward, not retroactively.

  • Sensitive data count — the visible per-log-group readout of what Audit actually found, so you know whether masking would even do anything before turning on Deidentify.
Data Protection isn't free$0.12 per GB scanned, on top of normal ingestion/storage — it scans every byte, so scope it to log groups that genuinely handle sensitive data rather than enabling broadly.

Contributor Insights: who's actually driving this

A rule against a log group, not a metric — ranks the top-N contributors (an IP, a tenant, a host) instead of just showing a total.

  • Keys — which log field identifies the contributor (e.g. a source IP, a customer ID).
  • Optional: sum a field instead of counting — rank by bytes transferred, not just event count.
  • Output is a graph, addable to a dashboard like any other widget.
Worked example

Rank VPC Flow Log source/destination IP pairs by total bytes transferred — the same "which one, specifically" question a plain aggregate metric can't answer.

Custom metrics: a metric filter already counts

A metric filter turning a log pattern into a number is a custom metric. EMF is the direct-from-code alternative.

{
  "_aws": { "Timestamp": 1735689600000,
    "CloudWatchMetrics": [{ "Namespace": "MyApp/Orders",
      "Dimensions": [["Service","Environment"]],
      "Metrics": [{ "Name": "ProcessingTime", "Unit": "Milliseconds" }] }] },
  "Service": "checkout", "Environment": "production", "ProcessingTime": 152
}
Worked example

A Lambda error-rate alarm via metric math (errors ÷ invocations) — a common, minimal use of metric math.

Composite & anomaly alarms

Was this threshold measured, or guessed?

  • Composite alarms — one root cause, one page, not three: ALARM(a) AND ALARM(b).
  • Anomaly detection — replace a guessed static threshold with a learned expected-value band.
Good habit

Set treat_missing_data explicitly on every alarm — avoids surprising evaluation behavior when a metric goes quiet.

Alarm mute rules: silence, don't disable

Stop notifications for a window without losing the alarm's evaluation history or turning it off entirely.

  • Scheduled mute — one-time or recurring window, built from a picker or a raw cron expression, targeting a chosen set of alarms.
  • Quick mute — select alarms in the list → mute for a preset window (15 min / 1 h / 3 h) or a custom time. For "I know this fires during my maintenance window," right when you need it.
Bonus

Existing mute rules can be applied retroactively to newly created alarms — one action instead of remembering to add each new alarm to a maintenance exception list.

Dashboards: put math front and center

Three widget types worth knowing: metric (a metric or metric-math expression), log (a Logs Insights query, rendered right on the dashboard), alarm status.

{ "type": "metric", "properties": {
    "title": "Checkout error rate (%)",
    "metrics": [
      [{ "expression": "errors/invocations*100", "id": "e1" }],
      ["AWS/Lambda","Errors","FunctionName","checkout-handler",{"id":"errors","visible":false}],
      ["AWS/Lambda","Invocations","FunctionName","checkout-handler",{"id":"invocations","visible":false}]
    ], "view": "timeSeries" } }

The same metric-math expression an alarm uses can drive a widget — viewed proactively, not just alerted on. A custom EMF metric slots into a widget exactly like any AWS-service metric.

Free cross-Region graphing

Mixing Regions in one graph needs zero extra setup — set region per metric. Cross-account is the part that needs Observability Access Manager.

Dashboard variables: one dashboard, not fifteen

Swap the target instead of duplicating the whole dashboard per target — fewer dashboards to keep in sync, and fewer $3/month line items.

  • Property variable — replaces every instance of a chosen field (a function name, an instance ID) across all widgets at once, via an input on the dashboard itself.
  • Pattern variable — a regex-based partial substitution, for when you need to transform part of a value rather than swap it wholesale.
CaveatA shared dashboard freezes the variable at whatever value it had when shared — viewers can't switch targets themselves.

X-Ray: search, don't just follow a link

  • Search directly — service(), responsetime, fault, groups.
  • Add an annotation, then filter by it — the same move as custom metrics: your own signal on default telemetry.
  • Service map — find matching traces, then see exactly where in the chain it broke.
subsegment.put_annotation('order_id', '12345')  # indexed, searchable
segment.put_metadata('request_body', payload)    # not indexed

X-Ray: everyday query patterns

Filter expressions answer "which traces match" — not "rank them." For that, a second layer exists.

service("payments-api") { http.status = 503 }
responsetime > 2
edge("api.example.com", "backend.example.com") { error }
The gapTrace search has no sort — it's always most-recent-first. "Top 10 slowest calls" or "error count by API" isn't answerable with a filter expression alone.
CloudWatch Transaction Search

Indexes 100% of spans as structured logs, queryable with Logs Insights' aggregation and sort — the native way to ask APM-shaped questions.

FILTER `attributes.http.response.status_code` >= 500
| STATS count(*) as errors by attributes.aws.local.service
| SORT errors DESC
| LIMIT 5

How a trace actually gets sampled

Service (OTel SDK/ADOT) → OTel Collector → X-Ray. The sampling decision is made once, by the root of the chain.

Why this mattersIf the root of a chain is untraced, nothing downstream gets a trace either. Event-driven hops (SQS/SNS/EventBridge) don't auto-propagate trace context across the boundary — that takes an explicit step, not just a config flag.

Observability: often a habit gap, not a setup gap

Container Insights

Enhanced mode dashboards automatically once enabled. The common failure is checking it only during fires, not as a habit.

ServiceLens

Zero extra setup wherever Container Insights + X-Ray data already flow — it's discoverable, not buildable.

Lambda Insights

A layer + an IAM policy, no code change — a low-cost signal to enable.

Bigger lifts

Application Signals (real instrumentation work) and Database Insights (RDS/Aurora-only, not applicable to DynamoDB).

Worth knowing about

Newer capabilities, for later

Not gaps to close this week — things worth having on the radar as needs come up.

Application Signals: golden signals + SLOs, built in

Automatic call-volume, availability, latency, and fault metrics per service, a generated service map, and first-class SLOs — without hand-rolled metric math.

  • SLOs defined directly against an auto-collected signal (e.g. "99% of requests under 300ms over a rolling 30 days") — burn-rate tracking comes free with the definition.
  • Instrumentation path matters: ADOT SDK + CloudWatch Agent is the default — it's the only path with full Container Insights integration and metrics on 100% of traffic regardless of trace sampling.
If tracing is already set up

Adopting this means reconfiguring an existing OTel Collector setup, not deploying new infrastructure — real instrumentation work, but not a from-scratch build.

Database Insights: query load meets app context

Sits on top of, and is gradually replacing, classic RDS/Aurora Performance Insights.

  • Standard mode — default, rolling 7-day history, same pricing as Performance Insights, optional 1–24 month retention.
  • Advanced mode — 1–24 month retention plus execution-plan capture and on-demand deep analysis, for an extra $0.0125 per vCPU-hour.
Direction of travelAfter 30 June 2026, only Advanced mode supports execution plans and on-demand analysis — Standard alone won't be enough for query-plan-level debugging going forward.
Pairs with Application Signals

When the calling service is also instrumented, a query-load spike traces back to which service caused it, instead of dead-ending at the database.

S3 Tables Integration: query logs with SQL, at rest

Exports Logs data into a managed Apache Iceberg table, queryable directly from Athena, Redshift, or EMR — no CloudWatch console required to read it.

  • No backfill — only events ingested after you associate a log source flow into the table.
  • Retention mirrors the source log group — not an independent long-term archive on its own.
  • No extra storage cost beyond normal ingestion — you pay only for the queries run against it.
Reach for it when

You need SQL-style analysis beyond what Logs Insights offers, or want to hand log data to a team that already works in Athena/Redshift rather than the CloudWatch console.

Bearer token authentication: logs without an AWS SDK

Lets a client that can't do AWS SigV4 signing — a plain OpenTelemetry exporter, a third-party tool — send logs with a simple Authorization: Bearer header instead.

  • Works with the OTLP /v1/logs endpoint too, not just the standard ingestion API.
  • The token is an IAM service-specific credential, shown once, with configurable expiry (1 to 36,600 days). Enabled per log group.
AWS's own guidancePrefer SigV4 with short-term credentials wherever the client supports it — this exists specifically as a fallback for clients that structurally can't.

Synthetics & RUM: narrower than you'd think

  • RUM ≠ marketing/behavior analytics — tools like GTM or Hotjar don't plug into alerting. RUM turns JS errors, HTTP errors, and Core Web Vitals into CloudWatch alarms next to every other infrastructure alarm.
  • Synthetics ≠ uptime pinging — a third-party monitor covers basic uptime. Synthetics' value: multi-step transaction canaries with screenshots on failure, in the same alerting pipeline, reaching non-public endpoints a third party can't.
